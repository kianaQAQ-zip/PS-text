## 三个值得说的技术点

**1. 为什么自己写重采样，而不是用 WPF 的 `TransformedBitmap`。** WPF 只暴露 `BitmapScalingMode` 四档档位，既不能选核，也不会在缩小时把核按比例展宽——而"缩小时展宽"正是抗混叠的关键。我没写空口结论，而是加了对照组：把 200px 宽的 1px 黑白竖条纹缩到 20px，

- 三次立方 → 灰度 `114~141`，基本就是中灰 127（正确抗混叠）
- 邻近取样 → **整片变成纯黑**（细节全部丢失，就是摩尔纹的另一面）

这一条断言同时证明了两件事：核展宽确实生效了，而且邻近模式确实没有抗混叠。

**2. 预乘 alpha 不是可选项。** 透明像素的 RGB 通常是 0。若直接对直通 alpha 做加权平均，半透明边缘会被这些"看不见的黑"拉暗，透明 PNG 缩放后出现黑边。实现上没有多一遍拷贝——水平遍的输出直接存成预乘值，垂直遍结束再统一还原。自检用"左半不透明红 + 右半 `(0,0,0,0)`"的图缩到一半宽度，断言半透明像素的红通道仍 `≥240`（实测 255）。

**3. "自动裁掉空白角"有严格解，不需要试凑。** 一个 W×H 矩形旋转 θ 后轴对齐包围盒是 `(W|cosθ| + H|sinθ|) × (W|sinθ| + H|cosθ|)`；凸多边形的极值点就是顶点，所以"旋转后的矩形落在原图内"等价于"它的包围盒落在原图内"。代入 `W = s·w`、`H = s·h` 解出最大内接比例 `s = min(w/(w|cosθ|+h|sinθ|), h/(w|sinθ|+h|cosθ|))`。200×200 转 15° 实测 `245×245 → 163×163`，且断言"**裁完之后一个背景色像素都不该存在**"——比只查四个角更难作弊。

## 两个实现决策

**单位换算的"真值"永远是像素。** 界面上的值只是同一份像素尺寸在不同单位下的表达：切单位时先换算回像素、再按新单位重新表达，所以**切单位不会悄悄改变实际输出尺寸**（自检断言 160px = 50% = 4.234cm，三种表达对应的都是 160×100px）。厘米按图片自身 DPI 换算，因此打印出来的物理尺寸是准的。

**校验放在 ViewModel，不放在滤镜里。** 尺寸超限属于可预期的用户输入，应该表现为"应用按钮不可用 + 一行说明"，而不是让滤镜抛异常去弹"执行失败"对话框。
