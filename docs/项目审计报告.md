# PS-text 项目完成度审计与不足分析

> 审计对象：`D:\Code\PS-text`（WPF 桌面图片编辑器，目标平台 Windows 7 SP1+）
> 审计时间：2026-10-07
> 审计视角：以"轻量化版 美图秀秀 / Photoshop"为标尺，检查**功能完成度**、**工程质量**与**产品化程度**

---

## 0. 一句话结论

**代码质量明显高于完成度：** 这是一个架构规范、测试扎实、算法正确的**技术底子（约 13.5k 行源码 + 4.4k 行自检），但它现在还不是"美图秀秀/PS"**——它更接近一个**「图片基础调整 + 打印」工具**。
真正卡住"像不像美图秀秀"的，不是代码写得不够好，而是**产品定位与功能面**之间的距离，以及**完全没有产品化**（图标/安装包/崩溃日志/版本控制）。

## 1. 规模与工程质量基线

| 指标 | 实测值 | 评价 |
|---|---|---|
| 业务源码行数 | 13,477 行 C# | 中型桌面项目体量 |
| 自检代码行数 | 4,384 行（内嵌于 exe） | 异常充沛，但**与产品同生共死** |
| 自检断言 | **142 项，全部 PASS** | 优秀（覆盖原子算法 + 端到端 + 竞态） |
| Release 产物 | `PS-text.exe` 263 KB | 极小，零第三方依赖 |
| 第三方 NuGet | **0** | 优势（离线可编）也是劣势（无生态） |
| 目标框架 | .NET Framework 4.8 | **Win7 需额外安装**，非系统自带 |
| 位数 | `AnyCPU` + `Prefer32Bit=true` → **32 位运行** | 大图有 OOM 风险 |
| 版本控制 | **无 `.git`** | ⚠️ 严重工程缺口 |
| 应用图标 | **无 `.ico`，csproj 无 `ApplicationIcon`** | ⚠️ 产品化缺口 |
| 崩溃日志 | 仅 `Debug.WriteLine`，**不落盘** | ⚠️ Release 下等于没有 |

### 做得对的地方（必须承认）

1. **服务抽象到位**：`IImageService / IDialogService / IDispatcherService / IPrintService` 全部有接口，VM 不碰任何 WPF 控件类型 → 可测试、可替换。这是很多桌面项目做不到的。
2. **滤镜是纯函数**：`BitmapSource in → WriteableBitmap out`，无副作用；并有"逐像素串行 vs 并行一致性"断言钉死。
3. **不可变快照 + 命令模式**：`ImageDocument`（不可变）+ `EditCommand` + `HistoryManager`（30 步 / 256MB 双上限 + 前一步 after 复用为后一步 before，30 步只占 31 份快照）——内存设计是本项目最漂亮的部分。
4. **踩坑记录即文档**：README 第 6 节把 20+ 个真实缺陷（跨线程解码、预览竞态、BGR/RGB 顺序、WPF 只读属性绑定崩布局……）写得清清楚楚，这在个人项目里非常罕见。
5. **性能做到位**：6MP 全分辨率调整 14ms（24 核并行）、3MP 半径 40px 高斯模糊 117ms（滑动窗口，与半径无关 O(1)/像素）。

## 4. Grilling：需要你拍板的 10 个设计决策

> 以下不是"改进建议"，是**质询**。请逐条给出你的判断，我按你的结论推进。

### Q1. 定位矛盾：你到底要做 A 还是 B？
- **A｜修图美化工具**（美图秀秀路线）：核心是美颜、滤镜库、贴纸、一键成图 → 需要人脸检测/磨皮算法/GPU 或第三方 SDK（如 OpenCVSharp、人脸关键点模型），**技术栈与当前项目几乎不重叠**。
- **B｜办公图片处理工具**（裁剪、加字、加水印、打印、批量）：核心是**准确、快速、不丢画质** → 当前项目**已经完成 80%**，只需补 P0-6 / P1-4 / P1-6。
- **你的答案是什么？** 这决定了后面所有工作量。**当前代码全部指向 B。**

### Q2. 用户画像：Win7 用户真的需要"美颜"吗？
愿意留在 Win7 的，多是**政企内网 / 老旧设备 / 特定行业机**。这些场景的高频需求是：**证件照排版、扫描件处理、批量加水印、打印归档**——恰好是 B。你确定要把研发投在美颜上？

### Q3. 为 Win7 付出的代价，你算过账吗？
坚持 `net48 + Win7` 意味着放弃：.NET 6/8、SkiaSharp/ImageSharp（真正的 WebP/AVIF）、ModernWpf、`Span<T>`/`SIMD` 便利、现代 CI。Win7 已于 2020 年停止支持。
**问题：目标用户里，实际还在跑 Win7 的比例是多少？如果是"我自己的老电脑"，那这个约束的 ROI 极低。**

### Q4. 32 位是笔"隐性负债"
`Prefer32Bit=true` 让进程最多用 ~1.6GB。设想用户打开一张 600dpi A4 扫描件（约 35MP ≈ 140MB 未压缩），叠加 30 步历史 + 预览缓冲——**崩溃概率不低**。
**问题：你的目标用户会不会处理大图？会，就必须改 64 位优先。**

### Q5. `WmpBitmapEncoder` 是 JPEG XR，不是 WebP。改还是留？
现在这套"压缩快照"在功能上能跑（JPEG XR 是无损的），但**文档和命名是错的**。
- 留：修正所有注释/README/属性名（`IsWebP` → `IsJpegXr`），成本 10 分钟。
- 换：引入真 WebP 需要第三方库，破坏"零依赖"。
**你选哪个？我倾向"留 + 改名"——但你必须知道自己在用什么格式。**

### Q6. 撤销历史：压缩快照 vs 命令重放，谁更"轻量"？
当前每步编辑都要 **JPEG XR 编解码一次**（大图上就是几十到几百 ms 的隐藏开销）。而 `EditCommand`（命令模式）其实**已经具备"重放"的基础**——保留原图 + 重放命令，内存只占 1 份原图，且天然支持"跳到第 N 步"。
**问题：你更看重"撤销显示快"，还是"内存最省 + 可跳步"？这是架构级取舍，现在改还来得及。**

### Q7. 无 git —— 是疏忽还是有意？
13.5k 行 + 142 项自检，全靠一个 exe 兜底。一次误操作就可能毁掉整个项目。
**要不要我现在就 `git init` + 首次提交（含 `.gitignore`，排除 `build/`）？** 这几乎是零成本、纯收益。

### Q8. 这是"产品"还是"技术演示"？
- 产品 → P0-1~P0-5 **全部必须补**（图标、安装包、崩溃日志、未保存提示、文件关联）。
- 演示/作品集 → 可以只补 P0-2（日志）以保证演示不崩，把精力放在功能广度。
**你的目标是什么？这决定 P0 的取舍。**

### Q9. 破坏性编辑：用户会不会反复改文字/边框？
现在文字和边框**一旦应用就烧进像素**，想改字号只能撤销重来。美图/PS 都靠图层实现非破坏性。
**问题：你的用户会"加字 → 看图 → 再调字号"吗？会，就得把 `EditCommand` 升级为"操作栈重放"模型（可无损回退到任意一步再继续编辑）。**

### Q10. 批量处理要不要进范围？
商业图片工具的刚需是"一次处理一堆"。你已有批量打印的队列骨架（`MainViewModel.Print.cs`），把它扩展成"批量套滤镜/加水印/改尺寸/导出"是**复用成本最低、用户感知最强**的一条增量。
**要不要把它列为下一个里程碑？**

**偏差 1：M2 的重心从"加水印"翻到了"去水印"。**
7.2 把「非破坏性水印与文字」升格为 P0，是按"办公场景要加字"设想的。
实际你拍板的是 "**水印的话最重要的是消去水印的功能**"，于是 M2 先做了
**修补/消除**（智能填充 + 仿制图章 + 区域历史），非破坏性标注排在后面。
这个翻转让 M2 比原估的 2.5 天重得多，但也让产品有了相对竞品最硬的一块差异。

**偏差 2：Q6 的"改用命令重放"没有采纳，改成三种撤销模型共存。**
当时的建议是在"压缩快照"和"命令重放"二选一。实际做下来发现**二选一本身就是错的**：
仿制图章这类笔刷编辑**无法用参数回放**（一次涂抹是几十个采样点的距离场结果），
非破坏性标注又**必须**用对象而不是像素（否则改不了参数）。最终按编辑类型分三种模型：

| 模型 | 用在哪 | 代价 |
|---|---|---|
| 整幅压缩快照 | 滤镜 / 裁剪 / 缩放 / 旋转 | 12MP 约 17 MB/步 |
| 区域历史（只存改动包围盒前后像素） | 仿制图章 | 一笔 200×200 约 320 KB（比整幅省 50 倍） |
| 对象 + 对象列表快照 | 非破坏性标注 | 几百字节/步 |

**偏差 3：7.4 里"复用打印队列骨架"这条低估了复用面。**
批量流水线真正复用的不只是队列骨架，还有全部滤镜纯函数：五个步骤（缩放/调整/翻转/边框/水印）
背后**一个算法都没新写**。新写的全是"编排 + 边界"——命名防覆盖、预览缩放换算、逐张失败隔离。
结论：把能力做成**纯函数**，复用成本会趋近于零；这次验证了一次。
