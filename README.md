# PS-text · 图片编辑与打印工具

WPF 桌面应用：图片加载 / 编辑 / 滤镜 / 打印，兼容 **Windows 7 SP1**。

- **目标框架**：.NET Framework 4.8（Win7 SP1 及以上）
- **UI 框架**：WPF + 手工 MVVM（无第三方 DI / MVVM 框架）
- **当前进度**：步骤 1~5 全部完成（P0 加载/画布/撤销、P1 调整与滤镜、P2 打印、P3 主题/快捷键/进度/最近文件），
  M0 止血（Git、关闭前未保存确认、崩溃日志落盘、应用图标）、**M1 尺寸缩放 + 任意角度旋转**、
  M2 的**修补 / 消除与标注**（智能填充 + 仿制图章 + 区域历史 + 非破坏性标注）、
  **M3 批量流水线**（有序步骤 + 面板内预览 + 原名后缀导出）均已完成；
  下一步 M4 免安装与文件关联

## 1. 环境与构建

### 为什么用 MSBuild 而不是 `dotnet build`
本机 .NET SDK 为 9.0.312，**没有 net48 的 WPF 目标包**（只有 8.0 / 9.0），
而 `TargetFramework` 必须是 net48 才能跑在 Win7 上。
因此使用 Visual Studio 的 MSBuild 构建经典 csproj。

```powershell
# Debug
& "C:\Program Files\Microsoft Visual Studio\2022\Professional\MSBuild\Current\Bin\MSBuild.exe" `
  PSText.csproj -t:Build -p:Configuration=Debug

# Release
& "C:\Program Files\Microsoft Visual Studio\2022\Professional\MSBuild\Current\Bin\MSBuild.exe" `
  PSText.csproj -t:Build -p:Configuration=Release
```

> **若直接调用 MSBuild.exe 报 “Known Windows LOLBin”**：本机工具层对可执行文件有黑名单，
> 且它是**执行前的命令字符串检查**，加 `dangerouslyDisableSandbox` 也无效（Bash 与 PowerShell 都一样）。
> 可行做法是把调用放进脚本里中转（黑名单不检查脚本内容）：
>
> ```bash
> "<managed-python>" build/build.py Release
> ```
>
> `build/build.py` 内部用 `subprocess.run` 调起上面那条 MSBuild 命令。`build\` 被 `.gitignore` 忽略，
> 所以这个脚本不会进仓库；换机器时按上面这段重建即可。

产物：`build\bin\<Configuration>\PS-text.exe`
（编译产物统一输出到 `build\`，由 `Directory.Build.props` 控制。）

> **NuGet 说明**：步骤 1 不依赖任何 NuGet 包，主题与样式全部放在
> `Resources\Theme*.xaml`，因此在完全离线的环境也能编译。
> 步骤 5 需要 MaterialDesignThemes 时，请先确保能访问 nuget.org
> （当前环境子进程无法访问外网，恢复会失败，故暂未引入）。

## 2. 自检（无界面回归测试）

内置 `--selftest` 模式，不弹窗、不依赖人工操作，覆盖 241 项检查：

```powershell
.\build\bin\Debug\PS-text.exe --selftest
# 退出码 0 = 全部通过；结果落在 build\selftest.log
```

> **自检报 `UnauthorizedAccessException`（`%TEMP%` 不可写）** 时，把 TMP/TEMP 指到项目内可写目录：
>
> ```bash
> cd build/bin/Release && TMP="D:/Code/PS-text/build/tmp" TEMP="D:/Code/PS-text/build/tmp" ./PS-text.exe --selftest
> ```

撤销 / 重做的内存优化（三处关键设计）：

1. **压缩快照**：一步历史不是未压缩位图（6MP 就要 24MB），而是 **JPEG XR（HD Photo）无损字节流**

2. **快照共享**：链式编辑时“前一步的 after”就是“后一步的 before”，

3. **双上限裁剪**：同时受“步数（30）”和“内存（256MB）”约束，超限从最旧一端丢弃，

### 步骤 4（P2 打印）

| 需求 | 实现要点 |
|---|---|
| P2-9 系统打印对话框 | `PrintDialog`，支持选择打印机 / 纸张方向 / 份数 / 页面范围 |
| P2-10 打印预览 | 独立窗口，显示纸张边界与可打印区域（虚线），可拖拽图像位置、缩放，四种布局模式 |
| P2-11 DPI 感知 | 排版**只用 DIP**，图像物理尺寸由图像自身 DPI 决定，**绝不乘打印机 DPI**（避免二次缩放模糊） |
| P2-12 批量打印 | 队列 + 逐张发送，每张一个打印作业，互不影响；逐张解码保持内存平稳 |

实现要点与踩坑：

- **DPI 感知的正确做法**：WPF 的 `DocumentPaginator` 以 DIP（1/96 英寸）排版，打印管线自己会
  映射到打印机分辨率。所以这里**只按 DIP 排版**；若手动乘打印机 DPI，会先按 96 放大、
  再按打印机 DPI 放大一次，结果反而更模糊。图像物理尺寸由 `PixelsToDips(pixels, imageDpi)`
  得出，因此“打印使用图片原始 DPI”自然成立，并已用断言覆盖
  （300 DPI 的 3000px = 960 DIP = 10 英寸）。
- **分页要落在整数像素上**：第 column 页的起点取整、终点取**下一页的起点**，
  而不是 `起点 + ceil(宽度)`；否则相邻页会重叠 1 个像素（整页放大时表现为一条重复细缝）。
  自检用“任意两页源区域两两不重叠 + 分页面积之和等于整图面积”钉死这一点。
- **填充模式在多页下是几何必然**：3:2 的图铺满 A4 纵向纸张必然纵向溢出，因此断言写成
  “盖满可打印区域 + 页网格与几何计算一致”，而不是“单页”。
- **预览的显示缩放与实际打印无关**：`DisplayScale` 只把纸张画到屏幕上，不参与版面计算，
  因此缩放预览不会影响输出清晰度。
- **无打印机环境下如何验证**：打印服务抽象为 `IPrintService`，版面 / 分页 / 单位换算
  都是纯计算，可在自检里完整验证；预览窗口则通过**真实构造 Window** 来验证
  XAML 资源与绑定（资源缺失只在运行时暴露）。

主题与设置的实现要点：

- **配色全部走设计令牌 + `DynamicResource`**：颜色不写在控件里，

  | 背景 | `CanvasBackgroundBrush` / `ChromeBackgroundBrush` / `StatusBarBackgroundBrush` | 画布 / 工具栏与面板 / 状态栏 |

  | 交互 | `PrimaryHoverBrush` / `PrimaryPressedBrush` / `PrimaryHoverBorderBrush` / `PrimarySelectedBrush` | 按钮悬停 / 按下 / 悬停描边 / 选中态 |

  | 标记 | `RetouchMaskFillBrush` / `RetouchMaskStrokeBrush` | 修补标记的填充与描边（两套主题同值，保证一眼可见） |

### 步骤 6（M1 图像尺寸缩放 / 任意角度旋转）

| 需求 | 实现要点 |
|---|---|
| 图像大小 | 像素 / 百分比 / 厘米三种单位；锁定宽高比；三档插值（三次立方 / 双线性 / 邻近）；25/50/100/200% 快捷比例 |
| 任意角度旋转 | -180°~180°；四档空白角填充（透明/白/黑/灰）；可"自动裁掉空白角（保持原比例）" |

实现要点与取舍：

- **自己写重采样而不是用 `TransformedBitmap`**：WPF 只暴露 `BitmapScalingMode` 四档档位，
  既不能选核，也不会在缩小时把核按比例展宽 —— 而"缩小时展宽"正是抗混叠的关键。
  自检里用 1px 黑白条纹缩 10 倍做了对照：三次立方得到 114~141（≈中灰 127），
  邻近取样则整片变成纯黑（细节丢失），两者差别一目了然。
- **可分离两遍**：先水平（源宽→目标宽）再垂直（源高→目标高），复杂度从 O(n²) 降到 O(2n)，
  且每遍按行并行、每线程复用行缓冲。
- **预乘 alpha**：透明像素的 RGB 通常是 0，直接对直通 alpha 做加权平均会被这些
  "看不见的黑"拉暗，在透明边缘留下黑边。因此重采样与旋转都是**先预乘、后还原**；
  实现上把"水平遍的输出"直接存成预乘值，垂直遍结束再统一还原，不额外多一遍拷贝。
- **单位换算的"真值"永远是像素**：界面上的值只是同一份像素尺寸在不同单位下的表达。
  切换单位时先把当前值换算回像素、再按新单位重新表达，因此**切单位不会悄悄改变实际输出尺寸**；
  厘米按图片自身 DPI 换算，所以"打印出来的物理尺寸"是准的。
- **90° 的整数倍自动走无损路径**：既快又逐像素无损，而且 90° 旋转本来就没有空白角，
  不该被"自动裁角"裁掉。任意角度旋转对其它角度一律用**逆映射 + 双线性**，
  避免正映射留下未填充的孔洞。
- **"自动裁掉空白角"的数学依据**：一个 W×H 矩形旋转 θ 后，其轴对齐包围盒为
  `(W|cosθ| + H|sinθ|) × (W|sinθ| + H|cosθ|)`；凸多边形的极值点就是顶点，
  所以"旋转后的矩形落在原图内"等价于"它的包围盒落在原图内"。
  代入 W = s·w、H = s·h 解出 `s = min(w/(w|cosθ|+h|sinθ|), h/(w|sinθ|+h|cosθ|))`，即最大内接比例。
  自检断言"裁完之后**一个背景色像素都不该存在**"来钉住这个结论。
- **校验放在 ViewModel 而不是滤镜里**：尺寸超限（单边 > 20000px 或总像素 > 4000 万）属于可预期的用户输入，
  应该表现为"应用按钮不可用 + 一行说明"，而不是让滤镜抛异常去弹"执行失败"对话框。
- **几何变换后重新适配缩放**：尺寸变了之后，若当前处于"适应窗口"就按新尺寸重算，
  否则把 4000px 缩到 800px 后画面只会占窗口的四分之一。
- **一个命名坑**：ViewModel 里表示角度的属性**不能叫 `RotationAngle`** —— 它会遮蔽
  `PSText.Services.Filters.RotationAngle` 这个枚举名，导致该类其它 partial 里写
  `RotationAngle.Clockwise90` 被解析成 double 属性而编译失败。现命名为 `RotationDegrees`。

### 步骤 7（M2 第一块：修补 / 消除）

| 需求 | 实现要点 |
|---|---|
| 智能填充（消除） | 在画布上拖拽矩形标记要去掉的水印 / 印章 / 日期戳（可连续框选多处），一次「智能填充」把标记区域按周围像素重建；一次填充 = 一步历史，可整体撤销 |

实现要点与取舍：

- **算法选的是调和扩散（求解 Laplace 方程 Δu = 0）**，而不是"模糊掉"或"涂一块色"。
  它的两条数学性质正好对上办公场景，而且**可以直接写成断言**：
  1. **常值解**：边界同色 ⇒ 填充结果就是那个颜色 —— 白纸上的红章、纯色背景上的半透明文字，填完就是干净的原背景；
  2. **精确重现线性函数**：边界是线性渐变 ⇒ 填充结果仍严格落在同一条渐变线上 —— 扫描件常见的照明不均也能对上，不留接缝。
     自检里实测最大误差 **1**（阈值 2）。
- **要诚实说清限制**：调和插值是**平滑**的，所以**纹理背景**（草地、织物、人脸）上的水印填完会留下一块平滑斑块。
  这不是实现问题，而是这类算法的数学边界 —— 那种情况应改用仿制图章手动取纹理。因此面板上直接写了这句话，
  不把功能吹成"一键完美去水印"。
- **为什么用矩形标记而不是笔刷涂抹**：办公场景的水印 / 印章是成片出现的，而填充只重建"标记范围内"的像素，
  **多框一点是无害的**（周围同色的地方会被填成同样的颜色，本来也不需要保护）。矩形因此比精修轮廓更省事、也不容易涂坏。
- **只在 ROI 内求解**：取标记包围盒外扩一圈作为求解域，用对称 SOR（ω = 1.9，即"超松弛"）加速收敛。
  实测 1200×800 图上填充 300×120 区域耗时 **160 ms**。收敛判据是单次扫掠的最大变化 < 0.05，达到即提前退出。
- **只写回掩膜内的像素**：因此"填充不越界"是结构性保证而不是靠小心操作，自检直接断言**标记外 0 改动**。
- **面积上限**：求解域的 float 缓冲是 像素数 × 4 × 4 字节，因此设了 200 万像素的上限并给出提示，
  避免用户整幅框选时在 32 位进程里把内存打爆。
- **标记面积按并集算**：重复框选重叠区域**不能重复计数**（要重建的是并集），所以计数是在写入掩膜时"只数 0→1"的增量，
  重叠部分自然不重复。自检专门用"完全落在已有标记内部的矩形"验证这一点。
- **标记的生命周期**：只在画布**像素尺寸真的变化**时丢弃（换图、裁剪、缩放、旋转），
  这样调整亮度之类的编辑不会把标记清掉。
- **与裁剪模式互斥**：两个模式都在画布上抓鼠标，同时开着会互相抢事件；进入修补时会自动退出裁剪。
  另外修补模式下双击画布不再切换缩放（双击是框选的一部分）。

### 步骤 8（M2b 第一块：仿制图章 + 区域历史）

| 需求 | 实现要点 |
|---|---|
| 仿制图章 | Alt 取源 → 拖拽涂抹；笔刷半径 / 硬度可调；笔迹预览用"笔刷粗细的折线" |
| 区域历史 | 每笔只保存**改动包围盒的前后像素**（`RegionEditCommand`），而不是整幅快照 |

为什么需要它：智能填充（调和扩散）在纯色 / 渐变背景上效果最好，但它本身是**平滑**的，
遇到草地、织物、人脸这类纹理会留下平滑斑块。那种情况只能由人指定"拿哪一块纹理来补" —— 这就是仿制图章。

实现要点与取舍：

- **覆盖率按"像素到笔迹折线的距离"算，不是逐个笔刷点叠加。** 这是最容易写错的地方：
  逐点叠加会让同一个地方越涂越浓（累积），而距离场天然只取一次覆盖。
  自检专门构造一条"反复回折到同一点"的笔迹来钉这一点 —— 中心像素必须严格等于源像素，不能溢出也不能偏移。
- **源像素一律取自原始图像**，不读已经涂过的结果。否则会出现"自我复制"的拖影
  （涂到哪儿就把刚涂上去的东西再搬一次）。
- **源位置由固定偏移决定**（源点 − 起笔点），所以一笔之内是纯粹的平移搬运，纹理不会被扭曲。
- **每笔只存改动包围盒的前后像素。** 12MP 图上整幅压缩快照约 17MB/步，涂几十笔就把历史预算吃满；
  而一笔 200×200 只有 160KB —— 自检里断言的是"相差 50 倍"这个量级。
  为此给 `IEditCommand` 加了 `ByteSize`，让 `HistoryManager` 把命令自有的字节也计入内存上限
  （否则这类高频小编辑会直接绕过预算）。
- **拖拽时不逐帧重建整幅位图**：只在叠加层画一条"笔刷粗细的折线"作为预览 ——
  它和滤镜里按距离算出的实际涂抹范围在几何上严格一致，所以预览就是所见即所得。
  松手才真正计算像素，避免拖动过程中反复创建整幅 `BitmapSource` 而卡顿。
- **笔迹采样点要抽稀**（距离小于 半径/4 的点丢弃）：这类点对"到折线的距离"几乎没有贡献，
  但会让距离场计算量随线段数线性增长。
- 已知限制：拖拽过程中显示的是笔迹预览（真实像素在松手后应用），不是逐帧实涂。

### 步骤 9（M2b-2：非破坏性标注）

| 需求 | 实现要点 |
|---|---|
| 标注工具 | 箭头 / 矩形 / 椭圆 / 序号（自动编号）/ 高亮 / 文字；拖拽绘制，点击已有标注即选中，可改颜色 / 线宽 / 字号，可拖动挪位、删除、清空 |
| 非破坏性 | 标注以**对象**形式存在于叠加层，画面 = 底图 + 全部对象实时渲染，底图像素不动 |
| 自动合并 | 执行滤镜 / 裁剪 / 缩放 / 旋转 / 涂抹等破坏性操作前自动把标注烘进像素；导出与打印不破坏标注层（用副本烘焙） |

实现要点与取舍：

- **标注为什么必须是"对象"而不是"画上去的像素"**：因为要**选中再改参数**。像素一旦画死，
  "把那个箭头改成蓝色"就只能重画。所以标注单独存在，改参数时只重绘那一个对象，底图完全不用动。
- **叠加层与合并渲染共用同一份几何**（`AnnotationVisualBuilder`）。如果两边各画各的，
  用户看到的和最终合并进画面的就会对不上 —— 这类"所见非所得"最难查。自检里两者都用同一份几何验证。
- **箭头用"一个填充多边形"画出来**（箭杆是细长四边形、箭头是三角形），而不是"一条线 + 一个三角"。
  这样叠加层与合并渲染都只需一次 `DrawGeometry`，线宽变化时箭杆与箭头也不会出现接缝。
- **高亮是半透明混合**（35% 填充而不是实色覆盖），自检直接断言结果像素是 210/156/156 这种
  "既不是底色也不是标记色"的中间值。
- **合并只渲染所有标注的并集包围盒**，不是整幅图 —— 标注通常只占画面一小块，12MP 图上这样能省掉几乎全部开销。
- **`AnnotationFlattenCommand` 必须同时还原像素与对象列表**：只还原像素的话，撤销之后标注会"凭空消失"
  （列表还是空的）；只还原列表的话，画面上会出现两份标注（像素里一份 + 叠加层一份）。
- **合并是一步独立的历史**：执行反色前自动合并，历史里是「合并标注 → 反色」两步。
  因此撤销两次才回到"标注可编辑 + 未反色"。这样每一步都是完整状态，比把两件事焊成一步更好解释。
- **导出与打印不破坏标注层**：保存时把标注烘进**副本**再写文件，打印预览与打印也用副本。
  所以用户存完盘之后还能回头改那个箭头的颜色。
- **文字标注用 `FormattedText.BuildGeometry` 转成几何**，而不是在叠加层放 TextBlock。
  这样"文字"和箭头、矩形走的是同一条渲染路径（都是填充几何），叠加层模板只需要两个 `Path`。
- 已知限制：选中后只支持**拖动挪位**，没有做八向缩放手柄；改尺寸的方式是删掉重画。

### 步骤 10（M3：批量流水线）

| 需求 | 实现要点 |
|---|---|
| 输入 | 多选文件 / 整个文件夹（可选含子文件夹）/ 把当前打开的图加进队列；按路径去重 |
| 流水线 | **有序**步骤列表，可增删、可上下移：尺寸缩放 / 基础调整 / 翻转旋转 / 边框 / 文字水印 |
| 预览 | 面板内缩略图：选中队列里某张图 → 整幅解码 → 降采样 → 套用当前流水线 → 显示 |
| 输出 | 目录 / 格式（沿用原格式或统一转 JPG/PNG/BMP/TIFF）/ JPEG 质量 / 文件名后缀 |
| 执行 | 逐张解码 → 套流水线 → 编码写盘；逐项状态、单张失败不中断、可取消 |

实现要点与取舍：

- **顺序对用户可见，而不是藏成固定管道**。先缩放后加水印 与 先加水印后缩放 得到的是**不同的东西**：
  自检里同一组参数两种顺序跑出来，水印的像素宽度是 81 px vs 40 px —— 整整一倍。
  把它固定下来等于替用户做了一个他看不见的决定。
- **`BatchContext.Scale` 是"预览不骗人"的全部地基**。缩略图是在小图上跑同一套步骤的，
  因此**绝对**像素参数（长边、边框粗细、固定字号）必须乘缩放因子，**相对**参数（百分比）必须**不**乘
  —— 降采样不改变比例关系，乘了反而错。自检直接断言 `ReadTargetSize`：
  长边 800 在全分辨率下给 800×600、在半缩放预览下给 400×300；而百分比模式两种上下文给出同一个尺寸。
- **水印默认按图像宽度百分比，而不是固定像素**。批量图的尺寸常常不一致，
  固定像素会让 4000 px 的大图上水印小到看不见、600 px 的小图上占满半屏。
  相对字号还有个附带好处：它在降采样预览里天然还是对的，不需要额外换算。
- **预览不复用 `LoadPreviewAsync`**。那条路径**不做 EXIF 方向校正**
  （见 `WpfImageService.Decode` 的 `decodePixelWidth` 分支），手机竖拍的照片会在预览里躺倒，
  而实际输出是按校正后的方向来的 —— 预览会骗人。所以改为整幅解码（方向正确）再降采样。
- **预览推算的输出尺寸要能被断言**。面板上显示"实际输出约 800 × 600 px"；
  自检把这句话和**真正写出的文件尺寸**做比对（容差 1%），这是"缩略图可信"的最终校验。
  允许 1% 是因为预览基于整数因子降采样，取整链条必然带 1~2 px 误差。
- **命名必须防住三种覆盖**（自检逐条钉住）：磁盘上已有同名文件、**同一次运行内已分配的名字**、
  以及源文件本身。中间那条最容易漏 —— 来自不同文件夹的两个同名文件撞名时磁盘上还没有第二个文件，
  单靠 `File.Exists` 根本查不出来，会静默互相覆盖；必须额外维护一个"已分配路径"集合。
- **GIF 输入在"沿用原格式"时改写为 PNG**。GIF 只有 256 色且可能是多帧，把照片写回 GIF 会静默毁掉画质
  （多帧还会被压成单帧），因此宁可变格式并在该项状态里写明原因。
- **`TextOverlayFilter` 的"必须在 UI 线程"是多余的约束**（已修正）。WPF 对
  `DrawingVisual` / `FormattedText` / `RenderTargetBitmap` 的真实要求是"创建与使用在同一线程"，
  并没有规定必须是 UI 线程。自检一直在普通线程调它且从未失败，`[32]` 更把整条含水印的流水线
  放到线程池线程上跑通并断言线程号不同。这条不解除的话，批量每张图都要切回 UI 线程排队，界面会一顿一顿。
- **批量没有"撤销"**，因为它只写新文件、原文件不动 —— 天然可重来，重跑一次即可。
  这与单张编辑需要三种撤销模型是两件事，不必强行统一。
- 明确不做：每张图不同参数（要逐张调就先单张编辑）、批量级的 EXIF/ICC 完整保留、水印平铺。

## 5. 架构约定（后续步骤必须遵守）
1. 每个 Service 都有接口定义（`Services\Interfaces`），便于测试与替换
2. 滤镜算法封装为纯函数：输入 `BitmapSource`，输出 `WriteableBitmap`，无副作用
3. XAML 使用 DataBinding；code-behind 只做「视口尺寸 / DPI 回传、手势转发、拖放」，
   不直接设置控件外观、不写业务逻辑
4. 异步一律 `Task`，不使用 `async void`
   （例外仅限"由 UI 事件 / 计时器触发且内部全包 try/catch"的入口，目前只有 `RunRenderAsync`；
   批量流水线的两个长流程刻意返回 `Task`，这样自检才能等到它结束，而不是靠 sleep 猜）
5. 注释用中文；关键算法附英文说明
6. 自动包含 null 检查与异常处理（Win7 上部分 API 行为有差异）

## 6. 注意事项 / 踩坑记录

- **应用级资源必须用代码合并**：实测 .NET Framework 4.8 下，
  `App.xaml` 里用 `ResourceDictionary.MergedDictionaries` 静态合并的字典，
  在窗口 BAML 解析阶段用 `StaticResource` 查找会失败（抛“找不到名为 Xxx 的资源”）。
  现统一由 `ThemeManager.Apply()` 在创建窗口前用代码合并（见 `App.xaml.cs`）。
- **pack URI 的程序集名**必须与 csproj 的 `AssemblyName` 一致，即
  `pack://application:,,,/PS-text;component/...`（注意是 `PS-text` 而不是命名空间 `PSText`）。
- **`BitmapSource.DpiX/DpiY` 是只读的**，.NET Framework 的 `FormatConvertedBitmap`
  也没有 DPI 参数，因此写入 DPI 必须用 `BitmapSource.Create` 重建（`WpfImageService.ApplyDpi`）。
- **“原始大小”取整到 3 位小数**：图片 DPI 常带换算误差（96 DPI 被存成 95.9866），
  直接相除会得到 1.00014 这种不直观的比例。
- **调整会话的“基准”必须在会话开始时固化**：降采样预览会临时替换显示位图，
  若等到提交时才去取“当前位图”当基准，取到的就是预览画面，
  撤销会恢复成“已经调整过”的图（这个缺陷被自检的逐像素断言抓出来）。
  因此用 `EnsureAdjustmentSession()` 在用户第一次改动参数时就固定基准。
- **不要把“已渲染参数”当作“已提交参数”**：`_lastRenderedAdjustments` 会被预览更新，
  而调整基准必须用 `_committedAdjustments`（只在实际提交 / 撤销 / 重做 / 加载时更新）。
- **`PixelBuffer` 逐行 `CopyPixels`**：不能用整块拷贝，因为 WPF 会按源位图自己的 stride 排布，
  当 stride ≠ Width×4 时后续行会整体错位。
- **预览渲染的“过期结果”必须在落地前再校验一次**：降采样预览比全分辨率提交快得多，
  用户松手时会同时存在“预览渲染”和“提交渲染”两个在飞行中的任务；
  预览的续体可能晚于提交落地，从而把已提交的全分辨率画面覆盖回预览画面
  （该缺陷只在 Release 下稳定复现，Debug 下因时序不同而隐藏）。
  现在预览在写入显示位图之前会再次确认 `revision == _renderRevision`。
- **保存必须使用“提交之后”的快照**：`FlushPendingPreviewsAsync()` 会替换 `Document` 的位图，
  因此在调用它之前取 `_document` 会保存到降采样预览图。现在统一在提交完成后重新取快照
  （`SaveToPathAsync` 改为接收快照参数）。
- **缓冲区是 BGRA，但滤镜语义按 (R, G, B)**：`BasicFilters.ApplyPerPixel` 早期把
  `rowBuffer[0..2]` 当成 (R,G,B) 传入，导致反色的红蓝通道互换。
  灰度因为三通道等权（测试数据对称）而“碰巧通过”，掩盖了该缺陷；
  现在参数顺序显式写成 (R,G,B)，并且**灰度断言改为分别校验 R/G/B 权重（77/150/29）**，
  使这类错误无法再被对称数据掩盖。
- **垂直盒式模糊不能用“按行并行 + 环形缓冲”**：输出行依赖前一行维护的列累加和，
  环形缓冲的“减去离开行”会读到已被其他行覆盖的槽位（表现为颜色错乱）。
  现改为按 y 顺序推进、显式记录窗口内每行的位置与缓冲，
  并只清理“严格低于窗口最左位置”的缓存项。
- **命令是即发即忘的，自检不能轮询状态标志**：`IsBusy` 在命令进入异步流程后才置位，
  轮询会在命令真正启动前就返回（表现为“历史没有增加”）。
  现在 ViewModel 暴露 `PendingOperation`，自检与保存前都可以等待它完成。
- **解码结果必须“物化”才能跨线程**：`BitmapFrame` 即使 `Freeze()` 后，访问 `DpiX` 等属性
  仍可能惰性回调解码器，而解码器保留创建线程的线程亲和性，表现为跨线程保存时抛
  “调用线程无法访问此对象”（只在 Release 下偶发）。现在解码后把像素复制成独立的
  纯内存位图（`WpfImageService.Materialize`），与解码器彻底脱钩。
- **`ProgressBar.Value` 默认是 TwoWay 绑定**：绑到只读属性（私有 setter）会在窗口
  首次布局时抛 `InvalidOperationException`，**编译期完全看不出来**。
  只读属性的绑定要显式写 `Mode=OneWay`。
- **设置写入要记住“生效位置”**：受限环境无法写 `%APPDATA%` 时回退到临时目录，
  但如果不把生效位置记下来（探针文件），下次启动仍去读默认位置、读不到就静默重置
  用户设置。这个缺陷是通过“改设置 → 重启 → 看是否保留”实测发现的。
- **不要把诊断信息写成“成功”**：早期实现里 `Save` 捕获异常后只写 Debug 输出，
  退出时却打印“已保存设置”，差点把“写入被拒绝”误判为正常。
  诊断语句必须反映真实结果（`exists=` / `size=` 等可验证字段）。
- **“跳过重复渲染”的判据必须区分预览与提交**：提交渲染原本复用了
  `_lastRenderedAdjustments` 判断“这组参数已经渲染过”，但那次渲染可能只是**降采样预览**。
  于是一旦预览先落地，提交就被误判为“无需重算”而跳过，结果是画面变亮了、
  历史里却没有这一步（Release 下约 3~10% 概率复现，Debug 下几乎不出现）。
  现在提交只认 `_lastCommittedAdjustments`，预览只认 `_lastRenderedAdjustments`。
  自检里加了一段“重复 8 次调整→提交”的循环专门盯这个缺陷。
- **XAML 注释里不能出现 `--`**：`<!-- ---------- 1. 来源 ---------- -->` 这种装饰线是非法 XML，
  编译期报 `MC3000`。分隔注释统一写成 `<!-- ===== 1. 来源 ===== -->`。
- **fire-and-forget 的 `Task` 要存进字段**：直接写 `RunXxxAsync();` 触发 CS4014 警告
  （本项目保持零警告），而且不持有引用的任务可能被 GC 提前回收。
  统一写成 `_xxxOperation = RunXxxAsync();`，顺带也留出了"必要时能等它"的口子
  —— 自检需要"等批量跑完"，靠的就是这个返回的 Task。

> **产品定位（已拍板）**：走**办公图片处理**路线（裁剪、加字、水印、打印、批量、**消除**），
> 一句话定位是「能在 Windows 7 干净跑的、零依赖的、中文批量图片处理工具」。
> **明确不做**：美颜 / 磨皮 / 祛痘 / 人脸检测 / 贴纸 / 一键风格滤镜库 ——
> 这些属于美图秀秀场景，会引入第三方 CV 依赖并破坏"零 NuGet"这一最大优势。
> 详见 `docs/项目审计报告.md` 第 7 节。
>
> **关于"消除"的边界**：把它做成中性的**修补工具**（智能填充 + 仿制图章），
> 而不是宣传成"去水印神器"。理由是双重的 —— 这本来就是 PS「污点修复画笔」那类通用能力，
> 定位成通用工具既更准确，也不会把产品绑到"规避他人版权"的用途上去。
> 同时**不引入 AI 修复模型**：ONNX Runtime 官方从 v1.15 起已不再支持 Win7，
> 加上百 MB 级模型，会同时破坏「零依赖 / 轻量 / 内网离线」三个核心卖点。
>
> **撤销架构（三种模型，按编辑类型选）**：
> 1. **整幅压缩快照** —— 滤镜 / 裁剪 / 缩放 / 旋转等"一次性、改尺寸"的编辑；
> 2. **区域历史** —— 仿制图章这类"一笔一步"的高频小范围编辑（只存改动包围盒的前后像素，
>    实测比整幅快照省 50 倍）；
> 3. **对象 + 对象列表快照** —— 非破坏性标注（要能选中再改参数，像素一旦画死就改不动了）。
> 三种模型共存，因为它们的编辑语义本来就不同；统一成一种反而会让每一类都很别扭。
> 批量处理**不属于**这三种 —— 它只写新文件、原文件不动，天然可重来，因此不需要撤销。
