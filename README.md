# PS-text · 图片编辑与打印工具

WPF 桌面应用：图片加载 / 编辑 / 滤镜 / 打印，兼容 **Windows 7 SP1**。

- **目标框架**：.NET Framework 4.8（Win7 SP1 及以上）
- **UI 框架**：WPF + 手工 MVVM（无第三方 DI / MVVM 框架）
- **当前进度**：步骤 1~5 全部完成（P0 加载/画布/撤销、P1 调整与滤镜、P2 打印、P3 主题/快捷键/进度/最近文件），
  M0 止血（Git、关闭前未保存确认、崩溃日志落盘、应用图标）与 **M1 尺寸缩放 + 任意角度旋转** 已完成；
  下一步 M2 标注工具与非破坏性水印

---

## 1. 环境与构建

### 为什么用 MSBuild 而不是 `dotnet build`
本机 .NET SDK 为 9.0.312，**没有 net48 的 WPF 目标包**（只有 8.0 / 9.0），
而 `TargetFramework` 必须是 net48 才能跑在 Win7 上。
因此使用 Visual Studio 的 MSBuild 构建经典 csproj。

```powershell
# Debug
& "C:\Program Files\Microsoft Visual Studio\2022\Professional\MSBuild\Current\Bin\MSBuild.exe" `
  PSText.csproj -t:Build -p:Configuration=Debug

# Release
& "C:\Program Files\Microsoft Visual Studio\2022\Professional\MSBuild\Current\Bin\MSBuild.exe" `
  PSText.csproj -t:Build -p:Configuration=Release
```

产物：`build\bin\<Configuration>\PS-text.exe`
（编译产物统一输出到 `build\`，由 `Directory.Build.props` 控制。）

> **NuGet 说明**：步骤 1 不依赖任何 NuGet 包，主题与样式全部放在
> `Resources\Theme*.xaml`，因此在完全离线的环境也能编译。
> 步骤 5 需要 MaterialDesignThemes 时，请先确保能访问 nuget.org
> （当前环境子进程无法访问外网，恢复会失败，故暂未引入）。

内置 `--selftest` 模式，不弹窗、不依赖人工操作，覆盖 169 项检查：

```powershell

# 退出码 0 = 全部通过；结果落在 build\selftest.log
```

### 步骤 2（P0 撤销重做 + P1 基础调整）

| 需求 | 实现要点 |
|---|---|
| P0-3 撤销/重做 | 命令模式；**默认 30 步**（要求 ≥20）；历史存 **JPEG XR（HD Photo）无损压缩快照**而非原始位图副本 |
| P1-4 基础调整 | 亮度 / 对比度 / 饱和度 / 色温；**拖动降采样实时预览，松手后全分辨率提交** |

撤销 / 重做的内存优化（三处关键设计）：

1. **压缩快照**：一步历史不是未压缩位图（6MP 就要 24MB），而是 **JPEG XR（HD Photo）无损字节流**
   （由 WIC 自带的 `WmpBitmapEncoder` 完成 —— 注意它**不是 WebP**，.NET Framework 的 WIC 并未内置 WebP）；
   实测照片类图片约为原始像素的 **36%**（PNG 更大），30 步内存从数百 MB 降到几十 MB。
   编码后会**解回逐像素校验**，一旦发现不是真无损就自动回退 PNG，保证撤销绝不丢画质。
2. **快照共享**：链式编辑时“前一步的 after”就是“后一步的 before”，
   30 步历史只占 31 份快照而不是 60 份。
3. **双上限裁剪**：同时受“步数（30）”和“内存（256MB）”约束，超限从最旧一端丢弃，
   并保留其 after 快照，因此**裁剪后撤销链依然完整**（不会出现撤不动的空洞）。

调整的执行流程：

- 拖动滑块 → 参数变化 → 220ms 防抖 → **降采样（≤1400px）预览**，立刻可见
- 停止拖动 → 自动按**全分辨率**重算并提交，形成一次可撤销的编辑
- 连续拖动多次只占**一格历史**（与 Photoshop 调整层行为一致）
- 保存 / 另存为之前会先 `FlushPendingPreviewsAsync()`，
  保证写入文件的是全分辨率结果而不是预览图

滤镜算法：亮度/对比度/色温合并成三张 256 项查找表（逐通道 O(1)），饱和度用定点亮度插值；
≥200 万像素时按行并行（线程复用行缓冲），实测 6MP 全分辨率约 7ms、

### 步骤 3（P1 高级滤镜与几何变换）

| 需求 | 实现要点 |
|---|---|
| P1-5 反色/灰度/二值化 | 逐点运算，并行；灰度用 Rec.601 加权亮度 |
| P1-6 模糊/锐化 | 高斯模糊（滑动窗口盒式逼近，**与半径无关 O(1)/像素**）；USM 锐化（半径/强度/阈值） |
| P1-7 裁剪/旋转 | 自由裁剪（三分线辅助、可拖拽八向手柄）；90°/180° 旋转；水平/垂直翻转 |
| P1-8 边框/文字 | 三种预设边框（实线/内衬相框/柔和阴影）；文字水印（字体/字号/颜色/九宫格锚点/加粗斜体/投影） |

实现要点：

- **模糊**：可分离 + 滑动窗口盒式模糊，三次迭代逼近高斯（σ ≈ √(n·(w²−1)/12)）。
  实测 3MP 图半径 40px 约 **150ms**（若用朴素卷积会慢两个数量级）。
  边界用镜像取样，因此**纯色图模糊后颜色完全不变**（朴素零填充会让边缘变暗，这一点有断言覆盖）。
- **几何变换**全部无损：角度为 90° 倍数、裁剪按整数像素，不引入插值。
  裁剪区域自动收敛到图像范围，非法输入返回原图副本而不是抛异常。
- **文字**：由于排版依赖 WPF 字体渲染，用 `DrawingVisual` + `FormattedText` +
  `RenderTargetBitmap` 合成（在 UI 线程），再读回像素缓冲并走统一的撤销流程。
- 所有新滤镜都通过同一条 `ApplyOneShotAsync` 流程：
  提交待处理预览 → 记录撤销目标 → 后台纯函数计算 → 写入历史。
  因此**每一步都是可撤销的**，且不会阻塞 UI 线程。
- 面板改为分页式（当时为 调整 / 滤镜 / 边框文字；M1 增加「尺寸」页后共 5 页）；裁剪时画布叠加遮罩层，
  未选中区域半透明变暗并显示三分线。

### 步骤 4（P2 打印）

| 需求 | 实现要点 |
|---|---|
| P2-9 系统打印对话框 | `PrintDialog`，支持选择打印机 / 纸张方向 / 份数 / 页面范围 |
| P2-10 打印预览 | 独立窗口，显示纸张边界与可打印区域（虚线），可拖拽图像位置、缩放，四种布局模式 |
| P2-11 DPI 感知 | 排版**只用 DIP**，图像物理尺寸由图像自身 DPI 决定，**绝不乘打印机 DPI**（避免二次缩放模糊） |
| P2-12 批量打印 | 队列 + 逐张发送，每张一个打印作业，互不影响；逐张解码保持内存平稳 |

实现要点与踩坑：

- **DPI 感知的正确做法**：WPF 的 `DocumentPaginator` 以 DIP（1/96 英寸）排版，打印管线自己会
  映射到打印机分辨率。所以这里**只按 DIP 排版**；若手动乘打印机 DPI，会先按 96 放大、
  再按打印机 DPI 放大一次，结果反而更模糊。图像物理尺寸由 `PixelsToDips(pixels, imageDpi)`
  得出，因此“打印使用图片原始 DPI”自然成立，并已用断言覆盖
  （300 DPI 的 3000px = 960 DIP = 10 英寸）。
- **分页要落在整数像素上**：第 column 页的起点取整、终点取**下一页的起点**，
  而不是 `起点 + ceil(宽度)`；否则相邻页会重叠 1 个像素（整页放大时表现为一条重复细缝）。
  自检用“任意两页源区域两两不重叠 + 分页面积之和等于整图面积”钉死这一点。
- **填充模式在多页下是几何必然**：3:2 的图铺满 A4 纵向纸张必然纵向溢出，因此断言写成
  “盖满可打印区域 + 页网格与几何计算一致”，而不是“单页”。
- **预览的显示缩放与实际打印无关**：`DisplayScale` 只把纸张画到屏幕上，不参与版面计算，
  因此缩放预览不会影响输出清晰度。
- **无打印机环境下如何验证**：打印服务抽象为 `IPrintService`，版面 / 分页 / 单位换算
  都是纯计算，可在自检里完整验证；预览窗口则通过**真实构造 Window** 来验证
  XAML 资源与绑定（资源缺失只在运行时暴露）。

### 步骤 5（P3 主题 / 快捷键 / 进度 / 最近文件）

| 需求 | 实现要点 |

| P3-13 深色/浅色主题 | 跟随系统 / 浅色 / 深色三选一；运行时立即切换；配色全部走 `DynamicResource` |
| P3-14 快捷键 | 完整菜单 + 快捷键，详见下表 |
| P3-15 进度反馈 | `ProgressReporter`：**超过 200ms 才显示**，所有回调回 UI 线程 |
| P3-16 最近文件 | 最多 10 个、去重置顶、缺失文件标记并提示移除、持久化到设置文件 |

快捷键一览：

| 快捷键 | 功能 |

| Ctrl+O / Ctrl+S / Ctrl+Shift+S | 打开 / 保存 / 另存为 |
| Ctrl+Z / Ctrl+Y | 撤销 / 重做 |
| Ctrl+P | 打印预览 |
| Ctrl+T | 在浅色 / 深色间切换 |
| Ctrl+R | 刷新最近文件状态（探测文件是否还在） |
| Ctrl+0 / Ctrl+1 | 适应窗口 / 原始大小 |
| Ctrl+`+` / Ctrl+`-` | 放大 / 缩小 |
| `+` `-` `0` `1` | 同上（无修饰键版本） |

主题与设置的实现要点：

- **配色全部走设计令牌 + `DynamicResource`**：颜色不写在控件里，
  而是集中定义在 `Resources\Theme.Light.xaml` 与 `Resources\Theme.Dark.xaml`（同名 17 个键），
  由 `ThemeManager` 在切换时替换字典。控件一律用 `DynamicResource` 引用，因此切换立即生效。
  两个窗口 XAML 里**已无任何硬编码色值**。
- **两套主题必须定义完全相同的键集合**：只在一套里定义的键，切换时会保留旧值
  （典型症状：深色模式下局部仍是浅色）。自检会**逐个键比对两套主题**并在缺失时报错。
- **设计令牌清单**（新增颜色请沿用这套命名，便于将来替换实现）：

  | 分类 | 键名 | 用途 |
  |---|---|---|
  | 背景 | `CanvasBackgroundBrush` / `ChromeBackgroundBrush` / `StatusBarBackgroundBrush` | 画布 / 工具栏与面板 / 状态栏 |
  | 分隔 | `BorderBrush` | 面板与工具栏分隔线 |
  | 前景 | `ChromeForegroundBrush` / `SubtleForegroundBrush` | 主文字 / 次要说明文字 |
  | 强调 | `AccentBrush` | 强调文字与选中描边 |
  | 交互 | `PrimaryHoverBrush` / `PrimaryPressedBrush` / `PrimaryHoverBorderBrush` / `PrimarySelectedBrush` | 按钮悬停 / 按下 / 悬停描边 / 选中态 |
  | 遮罩 | `OverlayBrush` / `CropMaskBrush` | 加载遮罩 / 裁剪遮罩 |
  | 棋盘格 | `CheckerLightBrush` / `CheckerDarkBrush` | 透明图片底纹（深色主题用深灰） |
  | 辅助线 | `GuideBrush` / `PrintableAreaBrush` | 裁剪三分线 / 打印可打印区域虚线 |

- **`Ctrl` 组合键在文本框里也生效，无修饰键快捷方式会让路**：
  否则在“添加文字”的输入框里打字时，按空格会变成抓手、按 `+/-` 会变成缩放。
- **设置写入需要“位置探针”**：默认写到 `%APPDATA%\PS-text\settings.xml`；
  受限环境写不进去时回退到临时目录，**并把生效位置记到探针文件**，
  否则下次启动又会去读默认位置、读不到就静默重置用户设置（这个缺陷实测复现过）。
- **解码结果必须“物化”**：`BitmapFrame` 即使 `Freeze()` 后，访问 `DpiX` 等属性仍可能惰性
  回调解码器，而解码器保留创建线程的线程亲和性 —— 表现为跨线程保存时抛
  “调用线程无法访问此对象”，且只在 Release 下偶发。现在解码后把像素复制成
  独立的纯内存位图，与解码器彻底脱钩。
- **`DrawingBrush`（棋盘格底纹）的换色需要肉眼确认**：棋盘格是唯一"嵌套在画刷里的颜色"
  （`DrawingBrush` → `GeometryDrawing` → 颜色令牌），不同于普通控件的 `DynamicResource`。
  自检覆盖的是**令牌层**（两套主题键集合一致、每个令牌都能解析到对应颜色、
  关键令牌在两套主题下确实不同）；"已渲染窗口里这块底纹是否实时换色"我**没有实测过**，
  请切一次主题看一下棋盘格是否跟着变。若发现不跟随，把 `CheckerboardBrush`
  复制一份到两套主题字典即可（切换字典时整份画刷被替换）。

### 步骤 6（M1 图像尺寸缩放 / 任意角度旋转）

| 需求 | 实现要点 |
|---|---|
| 图像大小 | 像素 / 百分比 / 厘米三种单位；锁定宽高比；三档插值（三次立方 / 双线性 / 邻近）；25/50/100/200% 快捷比例 |
| 任意角度旋转 | -180°~180°；四档空白角填充（透明/白/黑/灰）；可"自动裁掉空白角（保持原比例）" |

实现要点与取舍：

- **自己写重采样而不是用 `TransformedBitmap`**：WPF 只暴露 `BitmapScalingMode` 四档档位，
  既不能选核，也不会在缩小时把核按比例展宽 —— 而"缩小时展宽"正是抗混叠的关键。
  自检里用 1px 黑白条纹缩 10 倍做了对照：三次立方得到 114~141（≈中灰 127），
  邻近取样则整片变成纯黑（细节丢失），两者差别一目了然。
- **可分离两遍**：先水平（源宽→目标宽）再垂直（源高→目标高），复杂度从 O(n²) 降到 O(2n)，
  且每遍按行并行、每线程复用行缓冲。
- **预乘 alpha**：透明像素的 RGB 通常是 0，直接对直通 alpha 做加权平均会被这些
  "看不见的黑"拉暗，在透明边缘留下黑边。因此重采样与旋转都是**先预乘、后还原**；
  实现上把"水平遍的输出"直接存成预乘值，垂直遍结束再统一还原，不额外多一遍拷贝。
- **单位换算的"真值"永远是像素**：界面上的值只是同一份像素尺寸在不同单位下的表达。
  切换单位时先把当前值换算回像素、再按新单位重新表达，因此**切单位不会悄悄改变实际输出尺寸**；
  厘米按图片自身 DPI 换算，所以"打印出来的物理尺寸"是准的。
- **90° 的整数倍自动走无损路径**：既快又逐像素无损，而且 90° 旋转本来就没有空白角，
  不该被"自动裁角"裁掉。任意角度旋转对其它角度一律用**逆映射 + 双线性**，
  避免正映射留下未填充的孔洞。
- **"自动裁掉空白角"的数学依据**：一个 W×H 矩形旋转 θ 后，其轴对齐包围盒为
  `(W|cosθ| + H|sinθ|) × (W|sinθ| + H|cosθ|)`；凸多边形的极值点就是顶点，
  所以"旋转后的矩形落在原图内"等价于"它的包围盒落在原图内"。
  代入 W = s·w、H = s·h 解出 `s = min(w/(w|cosθ|+h|sinθ|), h/(w|sinθ|+h|cosθ|))`，即最大内接比例。
  自检断言"裁完之后**一个背景色像素都不该存在**"来钉住这个结论。
- **校验放在 ViewModel 而不是滤镜里**：尺寸超限（单边 > 20000px 或总像素 > 4000 万）属于可预期的用户输入，
  应该表现为"应用按钮不可用 + 一行说明"，而不是让滤镜抛异常去弹"执行失败"对话框。
- **几何变换后重新适配缩放**：尺寸变了之后，若当前处于"适应窗口"就按新尺寸重算，
  否则把 4000px 缩到 800px 后画面只会占窗口的四分之一。
- **一个命名坑**：ViewModel 里表示角度的属性**不能叫 `RotationAngle`** —— 它会遮蔽
  `PSText.Services.Filters.RotationAngle` 这个枚举名，导致该类其它 partial 里写
  `RotationAngle.Clockwise90` 被解析成 double 属性而编译失败。现命名为 `RotationDegrees`。

## 5. 架构约定（后续步骤必须遵守）

1. 每个 Service 都有接口定义（`Services\Interfaces`），便于测试与替换
2. 滤镜算法封装为纯函数：输入 `BitmapSource`，输出 `WriteableBitmap`，无副作用
3. XAML 使用 DataBinding；code-behind 只做「视口尺寸 / DPI 回传、手势转发、拖放」，
   不直接设置控件外观、不写业务逻辑
4. 异步一律 `Task`，不使用 `async void`
   （唯一例外：`Drop` 事件处理器签名所限，已用 try/catch 全包）
5. 注释用中文；关键算法附英文说明
6. 自动包含 null 检查与异常处理（Win7 上部分 API 行为有差异）

## 6. 注意事项 / 踩坑记录

- **应用级资源必须用代码合并**：实测 .NET Framework 4.8 下，
  `App.xaml` 里用 `ResourceDictionary.MergedDictionaries` 静态合并的字典，
  在窗口 BAML 解析阶段用 `StaticResource` 查找会失败（抛“找不到名为 Xxx 的资源”）。
  现统一由 `ThemeManager.Apply()` 在创建窗口前用代码合并（见 `App.xaml.cs`）。
- **pack URI 的程序集名**必须与 csproj 的 `AssemblyName` 一致，即
  `pack://application:,,,/PS-text;component/...`（注意是 `PS-text` 而不是命名空间 `PSText`）。
- **`BitmapSource.DpiX/DpiY` 是只读的**，.NET Framework 的 `FormatConvertedBitmap`
  也没有 DPI 参数，因此写入 DPI 必须用 `BitmapSource.Create` 重建（`WpfImageService.ApplyDpi`）。
- **“原始大小”取整到 3 位小数**：图片 DPI 常带换算误差（96 DPI 被存成 95.9866），
  直接相除会得到 1.00014 这种不直观的比例。
- **调整会话的“基准”必须在会话开始时固化**：降采样预览会临时替换显示位图，
  若等到提交时才去取“当前位图”当基准，取到的就是预览画面，
  撤销会恢复成“已经调整过”的图（这个缺陷被自检的逐像素断言抓出来）。
  因此用 `EnsureAdjustmentSession()` 在用户第一次改动参数时就固定基准。
- **不要把“已渲染参数”当作“已提交参数”**：`_lastRenderedAdjustments` 会被预览更新，
  而调整基准必须用 `_committedAdjustments`（只在实际提交 / 撤销 / 重做 / 加载时更新）。
- **`PixelBuffer` 逐行 `CopyPixels`**：不能用整块拷贝，因为 WPF 会按源位图自己的 stride 排布，
  当 stride ≠ Width×4 时后续行会整体错位。
- **预览渲染的“过期结果”必须在落地前再校验一次**：降采样预览比全分辨率提交快得多，
  用户松手时会同时存在“预览渲染”和“提交渲染”两个在飞行中的任务；
  预览的续体可能晚于提交落地，从而把已提交的全分辨率画面覆盖回预览画面
  （该缺陷只在 Release 下稳定复现，Debug 下因时序不同而隐藏）。
  现在预览在写入显示位图之前会再次确认 `revision == _renderRevision`。
- **保存必须使用“提交之后”的快照**：`FlushPendingPreviewsAsync()` 会替换 `Document` 的位图，
  因此在调用它之前取 `_document` 会保存到降采样预览图。现在统一在提交完成后重新取快照
  （`SaveToPathAsync` 改为接收快照参数）。
- **缓冲区是 BGRA，但滤镜语义按 (R, G, B)**：`BasicFilters.ApplyPerPixel` 早期把
  `rowBuffer[0..2]` 当成 (R,G,B) 传入，导致反色的红蓝通道互换。
  灰度因为三通道等权（测试数据对称）而“碰巧通过”，掩盖了该缺陷；
  现在参数顺序显式写成 (R,G,B)，并且**灰度断言改为分别校验 R/G/B 权重（77/150/29）**，
  使这类错误无法再被对称数据掩盖。
- **垂直盒式模糊不能用“按行并行 + 环形缓冲”**：输出行依赖前一行维护的列累加和，
  环形缓冲的“减去离开行”会读到已被其他行覆盖的槽位（表现为颜色错乱）。
  现改为按 y 顺序推进、显式记录窗口内每行的位置与缓冲，
  并只清理“严格低于窗口最左位置”的缓存项。
- **命令是即发即忘的，自检不能轮询状态标志**：`IsBusy` 在命令进入异步流程后才置位，
  轮询会在命令真正启动前就返回（表现为“历史没有增加”）。
  现在 ViewModel 暴露 `PendingOperation`，自检与保存前都可以等待它完成。
- **解码结果必须“物化”才能跨线程**：`BitmapFrame` 即使 `Freeze()` 后，访问 `DpiX` 等属性
  仍可能惰性回调解码器，而解码器保留创建线程的线程亲和性，表现为跨线程保存时抛
  “调用线程无法访问此对象”（只在 Release 下偶发）。现在解码后把像素复制成独立的
  纯内存位图（`WpfImageService.Materialize`），与解码器彻底脱钩。
- **`ProgressBar.Value` 默认是 TwoWay 绑定**：绑到只读属性（私有 setter）会在窗口
  首次布局时抛 `InvalidOperationException`，**编译期完全看不出来**。
  只读属性的绑定要显式写 `Mode=OneWay`。
- **设置写入要记住“生效位置”**：受限环境无法写 `%APPDATA%` 时回退到临时目录，
  但如果不把生效位置记下来（探针文件），下次启动仍去读默认位置、读不到就静默重置
  用户设置。这个缺陷是通过“改设置 → 重启 → 看是否保留”实测发现的。
- **不要把诊断信息写成“成功”**：早期实现里 `Save` 捕获异常后只写 Debug 输出，
  退出时却打印“已保存设置”，差点把“写入被拒绝”误判为正常。
  诊断语句必须反映真实结果（`exists=` / `size=` 等可验证字段）。
- **“跳过重复渲染”的判据必须区分预览与提交**：提交渲染原本复用了
  `_lastRenderedAdjustments` 判断“这组参数已经渲染过”，但那次渲染可能只是**降采样预览**。
  于是一旦预览先落地，提交就被误判为“无需重算”而跳过，结果是画面变亮了、
  历史里却没有这一步（Release 下约 3~10% 概率复现，Debug 下几乎不出现）。
  现在提交只认 `_lastCommittedAdjustments`，预览只认 `_lastRenderedAdjustments`。
  自检里加了一段“重复 8 次调整→提交”的循环专门盯这个缺陷。
