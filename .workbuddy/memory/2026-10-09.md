### 关键设计结论（都写进了 README/MEMORY）
- **顺序影响结果**：同一组参数两种顺序，水印亮区宽度 81px vs 40px（整整一倍）。
  顺序是产品语义，不能藏成固定管道。
- **`BatchContext.Scale`** 是"预览不骗人"的地基：绝对像素参数乘 Scale、相对参数不乘。
  最终校验 = 预览推算输出尺寸 vs 真实写盘文件尺寸（实测 800×600 完全一致，断言容差 1%）。
- **命名防三种覆盖**：磁盘同名 / 同一次运行内已分配 / 源文件本身。
  第二条是真正的陷阱（磁盘上还没第二个文件，`File.Exists` 查不出来）。
- 水印默认"按图像宽度百分比"（实测 1200px 图占 19.2%、400px 图占 19.3%）。
- GIF 在"沿用原格式"时改写为 PNG 并在状态里写明原因。
- 批量**没有撤销**，因为它只写新文件 —— 刻意不做，而不是缺口。

### 顺带修掉的错误约束
`TextOverlayFilter` 一直注释"RenderTargetBitmap 必须在 UI 线程"，**这个约束不成立**：
WPF 只要求"创建与使用在同一线程"。证据：自检一直在普通线程调它从未失败；
这次把整条含水印的流水线放到线程池线程跑通并断言线程号不同（1 → 28）。
同时 `ApplyAsync` 从"同步返回已完成任务"改成真的 `Task.Run`，单张加字不再僵住 UI。

### 踩坑（新增，已记 README §6 + MEMORY）
- **XAML 注释里 `--` 是非法 XML**：`<!-- ---------- 标题 ---------- -->` → `MC3000`。
  分隔注释统一 `<!-- ===== 标题 ===== -->`。
- **fire-and-forget Task 直接写语句触发 CS4014**（项目保持零警告）→ 统一存进字段
  `_batchRunOperation = RunBatchAsync();`，顺带也留出"自检能等它"的口子。

### 为可测性做的两个刻意设计
- `internal Task RunBatchAsync()` / `RunBatchPreviewAsync()` 返回 Task（不是 async void）——
  自检要能等批量跑完，而不是 sleep 猜。
- `internal bool AddBatchQueueItem` / `internal ReadTargetSize` —— 让自检能直接钉去重与缩放换算。
